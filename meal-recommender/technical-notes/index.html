Choose your next meal from the food you actually cook.

Project page · Product case study · Nutrition specification

Meal Planner is a personal meal-planning web app that prioritizes your own recipes, available ingredients, cooking time, and recent meal history. Optional nutrition targets help put the next meal in the context of the rest of the day.

The project began with a recurring personal problem: choosing lunch and dinner for two while balancing nutrition, variety, kitchen supplies, and the effort of shopping. It is an independently scoped Product Management portfolio project, implemented with AI assistance.

What it does

Feature Behavior
Personal recipes first Add, edit, search, and delete recipes. Six labeled samples make the app explorable before building a library.
Contextual suggestions A guided flow collects meal, servings, time, date, and ingredients, then returns up to three ranked personal recipes with explanations.
Day and week planning Schedule, move, or resize meals. Mark consumption explicitly and log food outside the recipe library.
Optional nutrition Enter targets or use editable estimates. Keep actual intake separate from projected intake and identify incomplete totals.
Linked shopping list Review scaled ingredients before adding; merge compatible quantities and update requirements when linked plans change.
Lightweight inventory Track availability without mandatory quantities. Flag ingredients as running low or use soon.
Prepared leftovers Record remaining servings and offer ready-to-eat or reheating options alongside recipes.
Receipt import Review extracted grocery items before updating inventory. Optional on-device OCR or an external vision provider.
External recipe discovery Display up to two additional ideas from TheMealDB, separate from personal recipes and labeled as unverified.
Local persistence Store data in the current browser, with JSON export/import and deletion controls. No account required.

Try the core flow

  1. Open What should I cook? and select a meal, servings, time limit, date, and optional ingredients.
  2. Review personal suggestions, ingredient availability, and ranking explanations.
  3. Open a recipe and choose it for the meal. Choosing is planning, not logging consumption.
  4. Review ingredients and add selected requirements to the shopping list.
  5. Mark purchases and update inventory; mark the meal eaten when appropriate.

Navigation: Home · My Recipes · Plan · Shopping List. Inventory and leftovers have their own views; optional settings are in Profile.

Run locally

The core app uses HTML, CSS, and vanilla JavaScript ES modules. No package installation or application build step is required. Use Python 3, or another static HTTP server. From the root of the repository (which is private):

python3 -m http.server 8766

Open localhost:8766. Opening index.html directly through file:// is not supported because the app uses ES modules.

For browser-based logic tests, open localhost:8766/tests/. The title reports PASS or FAIL (n).

Recommendation logic

Recipes first pass hard filters for meal type, cooking time, required ingredients, and declared dietary restrictions. Passing recipes are ranked using:

Component Weight / rule
Ingredient availability Up to 50 points; available, running low, unknown, and unavailable are distinct states.
Nutritional fit Up to 25 points; uses known values and enabled targets. Missing values receive a neutral score rather than being treated as zero.
Recent variety Up to 25 points; considers repeated recipes over seven days and recent main-ingredient overlap.
Use-soon ingredients Up to 6 bonus points.
Mediterranean preference Up to 3 bonus points when enabled.

Ties favor quicker recipes. Bonuses never override hard filters. These weights are prototype heuristics, not validated measures of meal quality or user preference.

When nothing fits, the app explains which filters eliminated recipes and offers explicit adjustments. Allergy exclusions are not offered as one-click relaxations.

Data and integration boundaries

Capability Boundary
Nutrition No ingredient nutrition database is connected. Recipe values must be supplied; sample recipes do not contain invented nutrition.
Target estimates The implementation documents Mifflin–St Jeor and activity-based estimates. Estimates are editable and are not medical advice. See the nutrition specification for the detailed method.
Web discovery TheMealDB lookup uses one ingredient per request. Results lack cooking-time and nutrition data; time must be supplied before saving. This is not general live internet search across all selected ingredients.
Receipt OCR On-device Tesseract OCR requires an initial engine/language download and currently supports English. Every import requires review.
External vision Requires a user-provided API key and sends the receipt image to the configured provider. The supplied implementation report says this request was not verified live. Check the configured model and SDK before use.

Manual entry remains available when optional integrations are disabled or unavailable. No expiration dates or unreadable quantities are invented.

Privacy and limitations

  • App records are stored in this browser's localStorage; there is no account or cross-device synchronization. Clearing site data removes local records. Export backups when needed.
  • Optional network services are exceptions to local processing: external discovery sends an ingredient name; external vision sends a receipt image. On-device OCR downloads its runtime but processes the image locally.
  • Receipt images are described as transient; confirmed records and duplicate-detection metadata persist.
  • A browser-stored external-service key is suitable only for an explicitly understood personal prototype setup. A shared deployment needs a server-side integration rather than a secret embedded in client code.
  • Ingredient-name checks cannot guarantee allergy safety, product composition, or absence of cross-contamination.
  • Keto-style filtering is limited because carbohydrate intake is not tracked.
  • Unit conversion is limited to compatible units; mass-to-volume conversion is not inferred.
  • Stock is not automatically deducted after a meal. Unknown stock remains unknown.
  • The local-first design does not yet make this an installable offline PWA.

Architecture

index.html, styles.css
src/app.js             State, routing, persistence, and event handling
src/logic/             Recommendation, nutrition, diet, ingredients,
                       inventory, shopping, leftovers, receipts, storage
src/ui/                Page views and shared review panels
tests/                 Browser-run logic tests
docs/                  Feature and nutrition documentation
site/                  Showcase site assets and build script

Core domain logic is separated from view rendering. Hash routes support dedicated views for discovery, recipes, plans, shopping, inventory, receipt review, and settings.

Validation status

The implementation documentation supplied for this project reports 67 browser-run logic tests covering ranking and filters, unit-safe shopping calculations, partial nutrition, inventory, leftovers, receipt parsing, duplicate detection, and persistence recovery. It also reports manual checks of the main flow at desktop and 375 px mobile widths, including Tesseract OCR.

These are reported engineering checks, not evidence of user outcomes. This documentation revision did not independently rerun the tests or audit the source. The external vision request was explicitly not tested live in the supplied report. No multi-user usability study or measured reduction in decision time is claimed.

Product work and next steps

The product case study explains the personal problem, exploratory ETM benchmark, prioritization, iterations, and validation gaps.

Next priorities are to observe real use, test whether explanations help users choose, reduce recipe-entry effort, and validate recommendation weights before expanding integrations. Technical opportunities include URL import, sourced nutrition lookup, receipt-language support, cross-device synchronization, and automated UI tests.
